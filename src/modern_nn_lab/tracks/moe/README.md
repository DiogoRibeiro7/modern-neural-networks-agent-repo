# Sparse Mixture of Experts

**Claim level: educational implementation.** Sparse conditional computation with a
transparent router, compared against a dense ensemble reference and a dense feed-forward
baseline on a synthetic mixture-of-functions task.

## The claim under test

A model can hold many parameters while spending only a few per token. That makes **total**
and **activated** parameters different numbers, and a comparison quoting the wrong one is
not a comparison. Both are recorded for every run, alongside an analytic FLOP estimate, a
measured throughput, and the task metric.

| | total | activated | FLOPs/token |
| --- | ---: | ---: | ---: |
| `dense-ffn` | 8,737 | 8,737 (100%) | 16,384 |
| `dense-moe` | 8,961 | 8,961 (100%) | 16,512 |
| `sparse-top1` | 8,961 | 2,625 (29%) | 4,224 |
| `sparse-top2` | 8,961 | 4,737 (53%) | 8,320 |

`DenseMoELayer` is milestone 1 of the track prompt and is the *reference*, not the enemy:
it runs every expert on every token, so the gap between it and a sparse layer is the price
of sparsity, measured rather than argued about.

## ⚠ The renormalization trap

**Renormalizing the gate with `top_k=1` makes the router untrainable by the task loss.**

With one expert kept, the renormalized gate is `g / g ≡ 1` — a constant, whose derivative
with respect to the router's parameters is exactly zero. The expert's output gets multiplied
by a literal `1.0`, no gradient reaches the gate, and the only thing left shaping routing is
the auxiliary balancing loss, which pushes towards *uniform* — the opposite of
specialization.

This is measured, not asserted. Router gradient norm:

| setting | gradient norm |
| --- | ---: |
| `top_k=1, renormalize=True` | 6.7 × 10⁻⁹ (zero) |
| `top_k=1, renormalize=False` | 3.5 × 10⁻² |
| `top_k=2, renormalize=True` | 4.5 × 10⁻² |

It is pinned by `test_renormalizing_a_top1_gate_severs_the_router_from_the_task_loss`, and
it explains this track's headline result: top-1 routing failed to specialize while top-2
succeeded, and the cause was arithmetic rather than optimization difficulty. **Use
`renormalize=False` with top-1 routing.**

## Capacity and overflow

Each expert accepts `ceil(capacity_factor · N·k / E)` assignments; beyond that, assignments
are **dropped**. A token kept nowhere receives exactly zero from the layer, so the loss is
visible in the output rather than in a counter, and the residual connection carries the
token forward unchanged — overflow degrades a token to "not processed", never to "erased".

Priority is **slot-major**: every token's first choice is offered capacity before any
token's second choice, since a second preference displacing a first is the wrong trade at
equal cost.

## The load-balancing loss

The Switch-Transformer auxiliary loss, `E · Σ f_e P_e`. It equals **1** under uniform
routing and **E** under total collapse — a falsifiable pair of endpoints rather than a vague
"encourages balance", and both are asserted in the tests. It is computed *before* capacity
is applied, so it penalizes the imbalance that causes drops rather than being confounded by
the drops it caused.

## Measuring specialization rather than inferring it

Every token is generated by one of `K` known functions and that identity is recorded, so
"the experts specialized" is a claim about a confusion matrix. Each token splits into a
**selector** half that determines which function applies and an independent **value** half
the function acts on. Without that split a model could partly regress the target without
routing, and a failure to specialize would be indistinguishable from a task that never
needed it — a test confirms the selector half predicts the latent function at >0.85 while
the value half manages <0.45.

`specialization_purity` summarizes the matrix permutation-invariantly, since expert
identities are arbitrary. It must be read *beside* the utilization spread: two functions
sharing one expert still score well on purity alone.
