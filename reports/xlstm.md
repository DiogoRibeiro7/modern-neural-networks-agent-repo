# Track 02 — xLSTM

> Tables in this report are generated by `python scripts/report_xlstm.py` from the records

## 1. Claim level

**`educational implementation`** — see [`docs/claim_policy.md`](../docs/claim_policy.md).

The sLSTM and mLSTM recurrences are implemented from the formulation recorded in the
source registry and verified step-by-step against the textbook equations. There is no
fused kernel, no block-parallel formulation, and no language-model-scale experiment, so
nothing here is a reproduction of any published result.

## 2. Sources

See [`docs/source_registry.md`](../docs/source_registry.md#track-02--xlstm).

- Beck et al., *xLSTM: Extended Long Short-Term Memory*, arXiv:2405.04517.

## 3. Method

Full formulation, shape table, complexity analysis, and the five recorded deviations are
in [`src/modern_nn_lab/tracks/xlstm/README.md`](../src/modern_nn_lab/tracks/xlstm/README.md).

**Fairness controls.**

1. One shared training loop for every architecture.
2. Baseline widths are searched so their parameter counts match the xLSTM's. At equal
   width an LSTM, a GRU, and a Transformer differ by several times in capacity.
3. Each architecture selects its learning rate from the *same* grid on the *validation*
   split. The test split is scored once.
4. The gating ablation changes exactly one function — `_log_gate` — and nothing else.
5. Every seed is recorded; none is dropped.

## 8. Failures and instabilities

**No run diverged.** All 108 records have `status="success"`, and no non-finite loss was
observed in any configuration — the stabilizer holds.

**A correctness bug was found by the hand-computed test and fixed before these numbers
were produced.** It is recorded here because the failure mode is subtle and generalizes.

The mLSTM read-out applies the source's covering rule `h = C q / max(|nᵀq|, 1)`. The
implementation stores the *stabilized* state, which is the true state scaled by
`exp(-m_t)`. Rescaling numerator and denominator by the same factor leaves a ratio
unchanged — but `max(·, 1)` is **not** scale-invariant, so flooring the stabilized overlap
at a bare `1` silently computes a different function than the equations specify. The
correct floor in the stabilized representation is `exp(-m_t)`:

```text
h = (C̃ q e^m) / max(|ñᵀq| e^m, 1) = C̃ q / max(|ñᵀq|, e^-m)
```

A forward-pass smoke test would never have caught this: shapes, finiteness, and training
behaviour were all unremarkable with the wrong floor. What caught it was
`test_mlstm_matches_a_manual_two_step_calculation`, which re-derives two steps from the
published equations without the stabilizer and demands exact agreement. **Numerical
stabilization must be verified against an unstabilized reference, not merely checked for
finiteness.**

**Where the mechanism fails outright.** The mLSTM configuration cannot solve state
tracking: 0.589 ± 0.011 against a chance level of 0.5, while an LSTM with *fewer*
parameters reaches 1.000 ± 0.000. This is not a tuning failure and it is not noise; see
interpretation point 2.

## 9. Interpretation

**1. Exponential gating gives a small, task-dependent benefit — not a general one.**
Comparing the identical model with only `_log_gate` changed:

| task | exponential | sigmoid | verdict |
|---|---|---|---|
| copy | 0.409 ± 0.014 | 0.379 ± 0.016 | exponential better, intervals disjoint |
| selective recall | 0.283 ± 0.054 | 0.323 ± 0.054 | intervals overlap; no effect detected |
| state tracking | 0.589 ± 0.011 | 0.614 ± 0.016 | sigmoid better, intervals disjoint |

So at this scale the unbounded input gate helps where a payload must be *written and
retained* (copy), does nothing measurable for selective retrieval, and mildly *hurts*
where the state must be updated at every step. The honest summary is that exponential
gating is not a free improvement; it trades write-dominance for update stability.

**2. The mLSTM cannot do state tracking, and this is structural rather than empirical.**
Its recurrence is `C_t = f_t C_{t-1} + i_t v_t k_tᵀ` where both gates depend on `x_t`
alone. Conditioned on the input sequence, the state update is **affine in the state**, so
the map from prefix to state is a product of input-determined affine maps. Running parity
is not computable that way — it needs a state-dependent update. The measurements match the
prediction exactly:

- mLSTM: 0.589 at T=16, and 0.734 → 0.584 as T goes 8 → 16, i.e. decaying toward chance;
- LSTM, GRU, and the **sLSTM** variant of this same architecture: 1.000 ± 0.000.

The sLSTM variant is the decisive comparison, because it differs from the mLSTM variant
only by having memory mixing — gates that read `h_{t-1}` — which restores a state-dependent
update. One confound must be named: the sLSTM variant carries 8578 parameters against the
mLSTM's 4614, so it is not width-matched to its sibling. That confound is resolved by the
LSTM, which solves the task perfectly with **4946** parameters — fewer than the sLSTM and
close to the mLSTM. Capacity is not the explanation; the form of the recurrence is.

**3. Attention wins the copy task decisively, and that is expected rather than
disappointing.** The Transformer reaches 0.898 ± 0.14 against the best recurrent result of
0.477. Copying a payload after a fixed delay is exactly what direct positional access is
for, and at T=17 attention pays none of the quadratic cost that would eventually penalize
it. This result says nothing about long-context behaviour; it is reported because omitting
a baseline that wins would be selective reporting.

**4. Nothing separates the architectures on selective recall.** Every model lands between
0.205 and 0.323 with intervals that overlap, against a chance level of 0.125. All of them
learn *something* and none of them learns it well. At `d_model = 32` with two heads the
matrix memory holds 16×16 per head, and 500 sequences is little data. The correct
conclusion is that **this diagnostic did not discriminate at this budget**, not that the
architectures are equivalent.

**5. The tasks are deliberately left partially solved.** Accuracies of 0.3-0.5 look
unimpressive next to a saturated benchmark, but a task solved at 100 % by everything
discriminates nothing. The budget was chosen so the architectures remain separable —
which is what makes points 1 and 2 measurable at all.

**6. The implementation is 7× slower than an LSTM and this is not a property of the
architecture.** The mLSTM forward pass takes 15.1 ms against the LSTM's 2.0 ms at a matched
parameter count, because the recurrence is stepped in a Python loop while `nn.LSTM` calls
a fused kernel. The mLSTM's gates do not depend on the hidden state, so it is *in
principle* parallelizable over time — the sequential scan here is an implementation
choice, not a constraint of the mechanism. Note also that the sLSTM variant appears
*faster* (10.1 ms) than the mLSTM despite memory mixing, purely because a scalar state is
cheaper per step than a matrix one. **No number in this section should be read as evidence
about xLSTM's achievable speed.**

## 10. Limitations

1. Sequence lengths are 8-17. This is far below the regime where attention's quadratic
   cost matters, so the Transformer baseline is under no scaling pressure and the
   recurrent models get no structural advantage.
2. No fused or parallel kernel, so nothing here speaks to xLSTM's achievable speed.
3. Synthetic tasks only. No language modelling, and therefore no evidence about the
   claims the primary source actually makes.
4. The blocks are plain pre-norm residual wrappers, not the source's block design.
5. Small widths (`d_model` 32, one block) mean the matrix memory is small, and the
   selective-recall diagnostic did not discriminate between any two architectures.
6. The sLSTM variant is not width-matched to the mLSTM variant (8578 vs 4614 parameters).
   The LSTM comparison resolves that confound for state tracking but not in general.

## 11. Next experiments

3. Vary the number of stored pairs in selective recall against head width, to map matrix

4. Implement the chunkwise-parallel mLSTM formulation and verify it against the stepwise
