> `results/artefacts/experiment_index.json`. The comparison matrix is authored judgement and
> says so.

## 1. What this document is not

**There is no aggregate score, and there will not be one.** Ranking Kolmogorov–Arnold
networks, prior-fitted networks, flow matching, Mamba-3, JEPA and relational models with a
single number would require their metrics to be commensurable, and they are not: the
evidence table below contains accuracies, mean squared errors, energy distances, and probe
R-squareds, measured on unrelated synthetic data at unrelated scales. A mean of those
numbers would be arithmetic performed on incompatible units, and its ordering would be an
artefact of which tracks happened to pick metrics with larger dynamic range.

What follows instead: what each track actually measured, what claim that evidence supports,
and where the evidence is thin.

## 3. Claim-level audit

The integration prompt's first task is to audit every track against
[`docs/claim_policy.md`](../docs/claim_policy.md) and downgrade unsupported claims. That
audit ran and **changed three claim levels**.

The policy defines `educational implementation` as a mechanism "implemented from primary
sources". Five tracks read no primary source in this environment. Two of them were already
at `research prototype`; the other three — Prior-Fitted Networks, Sparse MoE, and Flow
Matching — were claiming `educational implementation` and have been downgraded. Nothing
about those implementations or their results changed; the labels were overstated.

The audit also exposed a gap in the policy itself: **`research prototype` was used by the
registry but never defined.** It is now defined, as the label for a mechanism built from a
specification without a primary source, and the precondition in `educational implementation`
is now stated explicitly rather than left as an adjective.

_**Peak memory is unpopulated everywhere**, and that is a deliberate refusal rather than an oversight: `profiling.peak_memory` measures only on CUDA and returns `None` on CPU instead of a misleading number. Every run in this repository was on CPU, so the field is empty by construction. The `flops_per_sample` schema field is likewise unpopulated everywhere; the one track with analytic FLOP counts (Sparse MoE) stores them in its own configuration instead, which is a real inconsistency rather than a hardware limit. `activated` is blank where conditional computation does not apply._
<!-- /generated:profiling -->

**Throughput numbers across tracks are not comparable, and within a track are barely
self-consistent.** The Sparse MoE track measured >3× variation between *architecturally
identical* variants on this shared machine. Any cross-track cost comparison built on these
figures would be measuring machine contention. The analytic FLOP counts are the only
trustworthy cost numbers in the repository, and only one track computes them.

## 6. What the eleven tracks establish, taken together

**The most reliable finding is methodological, not architectural.** Across eleven tracks,
the recurring result is that a headline number was wrong until a specific control was added,
and the controls that mattered were almost always about the *baseline* or the *measurement*
rather than the model:

- a shared learning rate left a baseline untrained and manufactured a 1000× win (KAN);
- a record-filename collision silently merged two datasets (TTT);
- deterministic learners made five seeds identical, which *reads* as evidence of stability
  (Nested Learning);
- a cost measurement timed a warm cache and reported an up-front cost as free (PFN);
- a verification used an estimator less accurate than the quantity it verified (Flow);
- two collapse metrics each misclassified a real case, in opposite directions (JEPA).

Every one of these produced a plausible, publishable-looking number. None was caught by the
task metric; each was caught by a control, an ablation, or a diagnostic that existed only
because the track prompt demanded it.

**Where the architectures actually won, they won narrowly and conditionally.** The pattern
across tracks with honest baselines is that the novel mechanism matches rather than beats,
and earns its place on a secondary axis:

- PFN matches per-task baselines on accuracy and wins on calibration and amortized cost;
- top-2 MoE matches the dense ensemble and wins on FLOPs;
- JEPA matches raw features on content and wins on nuisance invariance;
- the relational prototype loses on three regimes and wins decisively on the one about time.

Only two tracks showed a mechanism beating its baselines outright on the primary metric
(xLSTM on state tracking, Titans on long-distance retrieval), and both are on synthetic
tasks constructed to require exactly that mechanism.

**Three claims were shown to be untestable here rather than false**, which is a different
and more useful outcome than a negative result: Mamba-3's MIMO contribution (needs
accelerator decode), TabPFN's checkpoint (license-gated), and any relational foundation model
(inaccessible). Recording them as untestable keeps them open.

## 7. Remaining scientific gaps

These are the reasons this repository is a set of prototypes rather than a study.

1. **Five of eleven tracks were built without reading their primary source.** Their
   formulations follow the track prompts, so a systematic misreading in a prompt would
   propagate undetected into the implementation. Nothing in those five tracks can be cited
   as evidence about the published work it is named after.
2. **Every experiment is on synthetic data generated by this repository.** Each dataset was
   designed to isolate the mechanism under test, which makes the tests clean and makes
   generalization to real data entirely unevidenced.
3. **Peak memory is unmeasured everywhere** — correctly, since the utility refuses to guess
   on CPU, but it means the memory column of any efficiency claim is empty.
4. **Analytic FLOPs exist for one track.** The schema field is unpopulated across all 987
   records; Sparse MoE keeps its counts in track-local configuration instead.
5. **Seed intervals mostly cover initialization, not data.** Most tracks fix the dataset
   seed and vary only training, so the intervals are narrower than they appear and say
   nothing about variability across problem draws.
6. **No track ran on an accelerator**, so every throughput and scaling statement is
   CPU-bound and several mechanisms (MIMO, sparse dispatch) are specifically designed for
   hardware this study did not use.
7. **The reproducibility audit could not be run from a genuinely clean environment** on this
   host; see §8.

_A passing audit means the committed artefacts are internally consistent: records validate, the scaffold is complete, and configuration hashes are stable. It does NOT mean the numbers were reproduced from scratch — see `unverified`. Report regeneration is checked separately by `scripts/verify_reports_regenerate.py`; including it here would be circular, since writing this file changes the report that summarizes it._

Why the unverified steps could not be run:

- **clean dependency resolution via `poetry install`** — Fails on this Windows host because of path-length limits while unpacking Torch metadata. The quality gate is executed with the interpreter's installed toolchain instead, which runs the identical commands CI runs through Poetry — but a genuinely fresh resolution was never exercised here. CI does exercise it on Linux across Python 3.11-3.13.
- **results reproduced by re-running every suite end to end** — Not attempted. Several suites take 20-30 minutes each on this machine, and re-running all eleven would take hours. Determinism is exercised per track by seeded tests instead, which is weaker: it checks that a run repeats, not that the committed records are what a rerun produces today.

## 9. How to check any claim in this repository

1. Find the track's report in [`reports/`](.); every table there is regenerated from records.
2. Run `python scripts/verify_reports_regenerate.py` to confirm the reports match the records.
3. Look up the configuration hash in `results/artefacts/experiment_index.json` for the exact
   settings a number was produced under.
4. Run `python scripts/validate_results.py` to re-validate every record against the schema.
5. Re-run a track with `modern-nn run-track <key>` and compare.
